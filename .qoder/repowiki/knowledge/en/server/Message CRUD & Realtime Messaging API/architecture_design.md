Layered MVC-style module split across five files: `message.routes.js` registers Express routes under `/channels/:channelId/messages`, `/threads/:threadId/messages`, and `/messages/:messageId`, applying shared middleware (`requireAuth`, `validate`, `requireMessageAccess`) before delegating to handlers. The controller layer (`message.controller.js`) is thin — it only extracts `req.channel`, `req.thread`, `req.message`, `req.user`, `req.memberPermissions`, and `req.validatedQuery` and forwards them to the service, returning responses via `sendOk`/`sendCreated`. Business logic lives in `message.service.js`, which enforces channel/thread permissions (announcement channels, locked/archived threads), authorship checks, reaction toggling, poll voting/editing, cursor-based pagination, and emits WebSocket events through `../sockets/emitters` (`emitToRoom`, `emitToUsers`) plus server-wide notification deltas. Data access is isolated in `message.repository.js`, a thin MongoDB/Mongoose wrapper around the `Message` model with populate helpers for author fields and bulk delete methods scoped by thread/channel/server. Validation schemas are centralized in `message.validation.js` using Zod and reused by both route-level `validate` middleware and the controller/service boundary.
