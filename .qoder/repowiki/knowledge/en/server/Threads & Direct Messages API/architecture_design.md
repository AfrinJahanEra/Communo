Follows a layered MVC pattern split per domain (thread vs dm):
- Routes (`routes/thread.routes.js`, `routes/dm.routes.js`) declare Express routers, compose middleware (`requireAuth`, `validate`, `requireThreadAccess`/`requireDmAccess`), and mount handlers for thread lifecycle, participation, and DM open/list/send/update/delete/reaction/read endpoints.
- Controllers (`controllers/thread.controller.js`, `controllers/dm.controller.js`) are thin async wrappers around services, using `asyncHandler` and `sendOk`/`sendCreated` to normalize responses; they read authorization context from `req.channel`, `req.thread`, `req.dm`, `req.memberPermissions`, and `req.user`.
- Services (`services/thread.service.js`, `services/dm.service.js`) enforce business rules (creator-only edits, archive/lock state guards, friend/block checks for DMs, active-thread limits) and orchestrate repository calls. They emit real-time events via `emitToUsers` on mutations (read marks, new messages, deletions, reactions).
- Repositories (`repositories/thread.repository.js`, `repositories/dm.repository.js`) wrap Mongoose models (`Thread`, `DmChannel`, `DirectMessage`) with CRUD helpers, cursor-based pagination, per-user unread count maps, and response normalization (`toThreadResponse`, `toDmResponse`).
- Validation schemas live in `validations/thread.validation.js` and `validations/dm.validation.js` (Zod), reusing shared message schemas from `validations/message.validation.js` so threads and DMs share the same message contract.
Dependency direction is strictly one-way: routes → controllers → services → repositories → models; cross-cutting concerns (auth, validation, transactions via `withTransaction`, socket emitters, storage cleanup) are imported from sibling modules under `utils`, `sockets`, and `constants`.
